# API материалов — tpivt6_26-41

JUnit 5 + REST Assured, реальные HTTP-запросы, без UI и моков. Самостоятельный
модуль повторяет организацию UI-тестов, но не наследует backend `BaseTest`,
который подменяет файловое хранилище. Изменяются только `name` и `subjectName`.
Извлечение текста и генерация не проверяются.

## Запуск на Windows

Нужны Git, работающий Docker Desktop с Linux-контейнерами, Compose >= 2.24.4
и сеть для скачивания образов/зависимостей. Java на компьютере не требуется:
Backend собирается с JDK 25, тесты — с JDK 17 внутри Docker.

Из корня скачанного репозитория:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\materials-api.ps1
```

Скрипт выполняет `docker compose up` для отдельного проекта с уникальным именем,
используя основной `docker-compose.yml`, `compose.ci.yml` и `compose.api-test.yml`.
PostgreSQL и S3 получают одноразовые данные в tmpfs, их порты не публикуются.
Frontend не запускается. Текущий локальный стенд и `.env` не используются.
Не запускайте этот набор против старой, рабочей или общей пользовательской БД.
Все тестовые учётные записи создаются заново, материалы очищаются после каждого
варианта. В конце скрипт удаляет только свой Compose-проект; tmpfs-данные исчезают.
Не заменяйте имя проекта именем существующего стенда.

`.env.ci.example` содержит только уже существующие одноразовые тестовые значения.
Реальные пароли/ключи OpenRouter не нужны. Секреты не выводятся в отчёты.
Первый запуск может длиться несколько минут; код выхода не 0 означает ошибку
сборки, окружения, тестов либо очистки и не должен считаться успешной проверкой.

## Результаты

Gradle собирает тесты во внутренней папке контейнера. После запуска отчёты
копируются в подключённую папку Windows; код ошибки тестов сохраняется.
Это позволяет выполнять `clean`, не удаляя точку подключения Docker.

- `api-tests/build/reports/run-summary.md` — версия, ветка, время, окружение,
  команда, состояние запуска/очистки и хеш исходника тестов.
- `api-tests/build/reports/materials-http.md` — endpoint, входные данные,
  ожидаемый и фактический HTTP-коды для каждого запроса, включая подготовку/очистку.
- `api-tests/build/reports/tests/test/index.html` — итог каждого теста и ошибки
  проверок полей; HTTP 200 сам по себе не означает прохождения теста.
- `api-tests/build/test-results/test/*.xml` — результаты для будущего CI.

Если стенд не запустился, проверки не выполнены. Смотрите текущий `run-summary.md`:
старые отчёты при ошибке старта нельзя использовать как подтверждение нового запуска.
Скрипт не меняет результат неуспешных тестов на зелёный и не пропускает их.

Перед приёмкой приложите отчёт в карточку, заведите отдельные задачи для найденных
дефектов, укажите их ссылки и результаты перепроверки. Укажите PR, ревью другого
участника и независимое повторение по этой инструкции; после подключения CI —
ссылку на прогон проверенной версии. Эти пункты автоматически не подтверждаются.

## Покрытие согласованных кейсов

| Кейс | Проверки |
|---|---|
| TC-API-MAT-01 | PDF/DOCX/TXT с описанием/тегом и без них; 201, Location, чтение, список; дополнительно скачивание исходных байтов |
| TC-API-MAT-02 | Только собственные материалы, нет дублей, значения полей, пустой список |
| TC-API-MAT-03 | Детали, имя/размер/формат файла, теги и состояние обработки |
| TC-API-MAT-04 | Имя, затем предмет; сохранение остальных полей, отсоединение старых тегов, неизменность второго материала |
| TC-API-MAT-05 | 204 с пустым телом; отсутствие в списке, GET/повторный DELETE 404, второй материал сохранён |
| TC-API-MAT-06 | Пять операций без токена и с невалидным токеном; отсутствие изменений |
| TC-API-MAT-07/08 | GET/PATCH/DELETE отсутствующего и чужого UUID, неизменность данных владельца |
| TC-API-MAT-09 | Обязательные поля, длины, JSON, запрещённые поля PATCH, части multipart, PNG, поддельный PDF, пустой/некорректный файл, UTF-8, превышение 10 МиБ, неверный UUID |
| TC-API-MAT-10 | Конфликт названия при создании и переименовании, отсутствие перезаписи |

56 отдельных запусков JUnit, включая параметризованные варианты. Все HTTP-запросы
идут к настоящему приложению; содержимое корректных файлов создаётся автоматически.
Пустая страница PDF допустима для проверки хранения: качество/извлечение текста
в объём CRUD не входит.

JSON-часть multipart передаётся явными байтами UTF-8, чтобы кириллица не заменялась
на `?`. Сохранённые названия проверяются также при подготовке данных каждого теста.
В сравнении POST с последующим GET только временные поля допускают разницу до
одной микросекунды из-за точности хранения; остальные поля сравниваются точно.
Сравнения повторных GET и неизменности даты после PATCH остаются точными.

## Структура и запуск из IDE

`src/test/java/tech/genna/TY3/tests/api/MaterialsApiTest.java` — кейсы и HTTP-помощники.
У каждого теста `@DisplayName` либо параметризованное имя с номером исходного кейса.
Можно подключить `api-tests/build.gradle.kts` как отдельный Gradle-проект и запускать
класс/метод через JUnit. Для этого нужен JDK 17+ и **отдельный одноразовый стенд**.
Вручную выставляются `API_BASE_URL` и `API_TEST_DISPOSABLE=true`; не используйте
адрес текущего пользовательского стенда. Рекомендуемый воспроизводимый путь — скрипт.

Новые переменные, устанавливаемые скриптом/Compose (см. `.env.example`):
`API_BASE_URL`, `API_TEST_DISPOSABLE`, `API_TEST_VERSION`.
