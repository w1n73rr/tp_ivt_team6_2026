# API прохождения теста

Класс `AttemptPassingApiTest` расположен в `api-tests/src/test/java/tech/genna/TY3/tests/api/`. Он обращается к реальным HTTP endpoint backend. `AttemptPassingAssertionsTest` содержит unit-проверки тестовых утверждений.

## Окружение и первая подготовка

Используется существующий изолированный стенд из `../attempt-result/README.md`: backend, PostgreSQL, SeaweedFS и управляемая модель `GenerationUiTestServer`. Перед каждым независимым сценарием регистрируются синтетические пользователи и создаётся сохранённый тест. Известные ключи определяются серверной тестовой моделью. Во время прохождения используются существующие вопросы и endpoint попыток. Внешние OpenRouter/Cloud.ru не вызываются.

Нужны Docker Desktop с Linux-контейнерами и JDK 17+ для Java-тестов. Из корня репозитория, если `.env.result-api.local` ещё отсутствует, скопируйте `.env.example` в этот файл. Заполните POSTGRES_PASSWORD, JWT_SECRET, S3_ACCESS_KEY и S3_SECRET_KEY независимыми случайными значениями по корневому README. Ключи внешней модели оставьте пустыми. Существующий файл не перезаписывайте. Файл игнорируется Git.

Один раз подготовьте стенд либо обновите его после изменения backend:

```powershell
Set-Location "$env:USERPROFILE\Projects\tp_ivt_team6_2026"
docker compose --env-file .env.result-api.local -f api-tests/attempt-result/compose.yml up -d --build --wait
```

Первая подготовка включает скачивание зависимостей и сборку backend. Стенд использует собственный Compose-проект attempt-result-api и временную БД generation_ui_controlled, без подключения старой пользовательской БД. Адрес API — http://localhost:18085. Не запускайте одновременно проверки, переключающие режим управляемой модели. Временные данные остаются в БД до остановки стенда.

## Повторный прогон без Docker-сборки

При уже работающем стенде выполните:

```powershell
Set-Location "$env:USERPROFILE\Projects\tp_ivt_team6_2026"
$env:JAVA_HOME = 'C:\Program Files\Java\jdk-17'
$env:API_BASE_URL = 'http://localhost:18085'
$env:API_TEST_DISPOSABLE = 'true'
$env:API_TEST_VERSION = (git rev-parse HEAD)
.\tests\ui\gradlew.bat -p .\api-tests test -PattemptPassing
Invoke-Item .\api-tests\build\reports\tests\test\index.html
```

Укажите свой путь к JDK, если он отличается. API_TEST_VERSION должен соответствовать исходникам запущенного backend. Папка `tests/ui` содержит общий Gradle wrapper; Java-модуль этого набора — `api-tests`.

Для запуска кнопкой импортируйте Gradle-модуль `api-tests` в IDE. В конфигурации JUnit класса `AttemptPassingApiTest` задайте API_BASE_URL, API_TEST_DISPOSABLE и API_TEST_VERSION как в примере. Запускайте класс или отдельный метод кнопкой рядом с ним. Для unit-класса `AttemptPassingAssertionsTest` backend и переменные окружения не нужны. При Gradle-запуске укажите `-PattemptPassing`.

Предыдущий набор `AttemptResultApiTest` запускается как раньше с `-PattemptResult`. Подготовка данных используется совместно через методы с пакетной видимостью, логика этих методов не изменена.

## Входные данные и HTTP-контракт

Сценарии создают тесты на 5 и 10 вопросов для SINGLE_CHOICE, MULTIPLE_CHOICE, TRUE_FALSE. В управляемой модели правильный вариант single-choice — первый; multiple-choice — первые два; true/false — первый для чётного индекса вопроса с нуля и второй для нечётного. Тексты и UUID вариантов читаются из публичного теста, ключи правильности клиенту до завершения не передаются.

Старт/продолжение — POST `/api/quizzes/{quizId}/attempts`, заголовок `Idempotency-Key` с новым UUID. Новая попытка возвращает 201; повтор ключа либо продолжение единственной активной попытки — 200.

Сохранение — PUT `/api/attempts/{attemptId}/answers/{questionId}`. Пример тела для синтетического UUID варианта:

```json
{"selectedOptionIds":["11111111-1111-4111-8111-111111111111"]}
```

Очистка — `{"selectedOptionIds":[]}`. Для выполнения используйте UUID из ответа своей попытки. Завершение — POST `/api/attempts/{attemptId}/complete`, без тела. Повтор возвращает тот же сохранённый итог.

## Покрытие и соответствие кейсам

| Проверка | Кейсы и ожидаемый результат |
| --- | --- |
| Шесть сочетаний типа/размера | TC-PASS-01: 5/10 вопросов, три типа, совпадение с сохранённым тестом и сохранение порядка |
| Выбор/изменение/очистка | TC-PASS-03–08: PUT 200, повтор идентичного PUT возвращает тот же savedAt, чтение и продолжение восстанавливают выбор, пустой массив очищает ответ |
| Позиция продолжения | TC-PASS-08: currentPosition указывает первый вопрос без ответа, answeredCount не включает очищенные вопросы |
| Завершение и повтор | TC-PASS-12–15,18: точные счётчики, отдельные пропуски, повтор complete и параллельное complete дают неизменный итог, новый ключ после завершения создаёт пустую новую попытку |
| Точное оценивание | 0/1 по текущему OpenAPI. Multiple-choice проверяется для полного/переставленного набора, подмножества, лишнего неверного варианта, полного набора с неверным, только неверного и пустого ответа |
| Нет сессии/невалидный JWT | TC-PASS-16: старт, GET попытки, PUT ответа, complete — 401 и безопасное тело |
| Подмена ID | TC-PASS-17: два реальных аккаунта на одном стенде, чужие и отсутствующие тесты/попытки — 404, несвязанный вопрос — 404 QUESTION_NOT_FOUND; вариант другого вопроса/теста и случайный вариант — 400 |
| Невалидный ответ | Два ответа в single-choice, дубли, null, строка вместо массива и отсутствие поля — 400; собственные и чужие данные не меняются |
| Защита до завершения | TC-PASS-19: старт/чтение/сохранение без ключей и баллов, строгие поля вопросов/вариантов; результат активной попытки — 409 |
| Идемпотентный старт | Шесть одновременных HTTP-запросов с одинаковыми и разными ключами: ровно один 201 и один attemptId. Старый ключ остаётся связан с первой попыткой. Его использование для другого собственного теста — 409 |
| Конфликт записи и complete | Три независимых состязания: PUT может дать 200 или 409. В первом случае завершение учитывает принятый ответ; во втором остаётся пропуск. Повторное чтение и завершение подтверждают итог; запись после завершения даёт 409 |

Проверяются реальные принятые ответы HTTP. Повторение конкурентного сценария не гарантирует наблюдение обоих порядков планирования. Последовательные проверки отдельно подтверждают допустимую запись до завершения и запрет записи после него.

Приложенные кейсы содержат предварительные вопросы к PO. Для API используются закреплённые правила текущего OpenAPI: пустой массив очищает, одна активная попытка продолжается, новый ключ после завершения создаёт повтор, несвязанный вопрос даёт 404. Частичные баллы не начисляются. Согласование UI-элемента очистки и подтверждений относится к UI-приёмке. TC-PASS-02,09 и интерфейсные части 10–15 в этот HTTP-набор не входят. Принудительный отказ БД и потеря сетевого ответа не инжектируются; повтор после предположительной потери ответа проверяется повтором того же ключа/complete и чтением сохранённого состояния.

## Отчёты и завершение задачи

- HTML — `api-tests/build/reports/tests/test/index.html`.
- Обезличенный HTTP-журнал — `api-tests/build/reports/attempt-passing-http.json`. Он содержит версию, названия сценариев, пути и ожидаемые/фактические статусы, без тел ответов, токенов и паролей.
- Сохранённый локальный отчёт — `REPORT.md`, журнал — `reports/local-http.json`.

Каждый прогон заменяет текущие build-отчёты. В журнале подготовительные запросы отделены порядком от запросов прохождения. Новых переменных окружения и внешних ключей нет. Для будущего CI запускается та же Gradle-команда после подготовки стенда, ненулевой код означает сбой проверки.

Для закрытия задачи нужны PR, ревью и повторение другим участником, зелёный CI проверяемой версии. Локальные результаты обозначаются как локальные.

После проверок остановите только этот стенд:

```powershell
docker compose --env-file .env.result-api.local -f api-tests/attempt-result/compose.yml down
```

Его временная БД исчезнет. Для показа преподавателю оставьте стенд запущенным и выполняйте только Gradle-команду повторного прогона.
