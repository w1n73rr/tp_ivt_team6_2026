### Реальная модель в GitHub Environment DEV

Обычный браузерный CI исключает только тег `live-ml`. Все управляемые сценарии
генерации остаются обязательными: CI поднимает отдельные PostgreSQL/S3,
тестовый Java-сервер и nginx. Тестовый контроллер не включается в production JAR.
Этим сценариям ключ OpenRouter не нужен.

Для реального пути UI → backend → OpenRouter → COMPLETED → сохранённый тест
есть отдельный workflow «Реальная генерация DEV». Он запускается вручную только
из `dev`, использует одноразовый Compose и не публикует образы и не меняет ВМ.
Его успешный результат — отдельное доказательство интеграции с реальной моделью;
зелёный обычный CI не заменяет этот прогон.

В Settings → Environments создайте `DEV`. В Deployment branches and tags разрешите
только ветку `dev`. Добавьте Required reviewer — владельца/ответственного за ML.
Если тот же человек запускает и принимает прогон, не включайте Prevent self-review.
В Environment secrets добавьте `OPENROUTER_API_KEY`, в Environment variables —
`OPENROUTER_MODEL` с согласованным точным ID модели. Используйте отдельный ключ CI
с ограниченным бюджетом; серверный ключ не переиспользуйте. Значение не копируется
в `.env.ci.example`, YAML, Docker build args или frontend.

Ключ получает только шаг запуска backend в задании с `environment: DEV`, после
подтверждения защищённого окружения. Образы собираются до передачи ключа.
Создание Environment само по себе не создаёт сервер и не передаёт секрет на ВМ.
После принятия workflow и передачи `dev` в GitHub выберите Actions →
«Реальная генерация DEV» → Run workflow → `dev`, затем подтвердите окружение.
Отсутствие ключа/ID модели завершает прогон явной ошибкой. Сетевые ошибки, квоты и
некачественный ответ модели также могут сделать реальный прогон красным.

### Первый запуск на учебном сервере

Сервер использует три файла: основной описывает сервисы и постоянные volumes,
`compose.registry.yml` задаёт образы GHCR, `compose.server.yml` закрывает внутренние
порты, отключает сборку, ограничивает память и журналы и включает перезапуск.
Порядок файлов важен. `!reset` удаляет локальные порты, `!override` заменяет
порт frontend на публичный HTTP 80. Нужен Compose >= 2.24.4.

В каталоге `/opt/tpivt` разместите эти три файла и `.env.example` из одной принятой
версии конфигурации. Используйте только новую серверную БД. На сервере:

```bash
cd /opt/tpivt
umask 077
test -e .env || cp .env.example .env
chmod 600 .env
nano .env
```

Заполните четыре обязательных секрета независимыми случайными значениями;
для каждого используйте `openssl rand -hex 32`. OpenRouter-ключ указывается только
если нужен ML. Добавьте в `.env`:

```dotenv
IMAGE_TAG=sha-a22830c8ff62a1bf7d7c68bb0c5da34452ac0eab
SERVER_ORIGIN=http://84.54.56.192
```

Это первый проверенный релиз. Оба образа должны иметь один SHA-тег. Адрес замените
при переезде; здесь origin — схема, адрес и при необходимости порт, без пути.
Секреты не передавайте в Git, чат или аргументы команд.

```bash
sudo docker compose --env-file .env -f docker-compose.yml -f compose.registry.yml -f compose.server.yml config --quiet
sudo docker compose --env-file .env -f docker-compose.yml -f compose.registry.yml -f compose.server.yml pull
sudo docker compose --env-file .env -f docker-compose.yml -f compose.registry.yml -f compose.server.yml up -d --no-build --wait --wait-timeout 300
sudo docker compose --env-file .env -f docker-compose.yml -f compose.registry.yml -f compose.server.yml ps
curl -fsS http://localhost/ >/dev/null
```

`config --quiet` проверяет настройки без печати секретов. Успешный `--wait` означает
готовность healthcheck; дополнительно вручную проверьте вход, загрузку, скачивание
и удаление тестового материала через браузер. Не запускайте пишущий CI smoke
против сервера с пользовательскими данными.

Проект называется `tpivt-server`: не меняйте имя, иначе Compose выберет другие
volumes. PostgreSQL хранится в `tpivt-server_pgdata`, S3 — в
`tpivt-server_seaweeddata`. Пересоздание контейнеров сохраняет их; `down -v`
удаляет данные. Изменение пароля в `.env` не меняет пароль уже созданной БД.
Никогда не добавляйте `compose.ci.yml` к серверному запуску.

Наружу публикуется только nginx:80. Backend, PostgreSQL и S3 доступны в сети Docker.
В облачной группе безопасности оставьте HTTP 80 и SSH 22 с разрешённых адресов.
HTTP передаёт данные без шифрования: пока используйте только тестовые учётные записи.
Память контейнеров ограничена суммарно примерно 3.1 ГиБ; это стартовые лимиты
для ВМ 4 ГБ, их нужно проверить под нагрузкой. Логи ограничены 3 файлами по 10 МБ
на контейнер. `unless-stopped` восстанавливает контейнеры после перезагрузки ВМ,
но сам по себе не перезапускает контейнер только из-за статуса unhealthy.

На этом шаге резервное копирование, восстановление, автоматическое обновление
и откат ещё не настроены. Следующий релиз может запускать миграции Flyway:
откат образа не откатывает схему БД. До обновления данных нужен проверенный backup.

Для новой копии и новой базы данных скопируйте `.env.example` в `.env`, если файла
ещё нет. Заполните `POSTGRES_PASSWORD`, `JWT_SECRET`, `S3_ACCESS_KEY` и `S3_SECRET_KEY`
независимыми случайными значениями. Для каждого значения можно выполнить:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Результаты сохраняйте только в локальном `.env`, не в Git или переписке.
Без заполненных значений Compose откажется запускаться. Затем выполните:

```bash
docker compose up -d --build --wait
```

Нужен Docker Compose 2.24.4 или новее. Локальные адреса и порты заданы в
`.env.example`; веб-интерфейс по умолчанию доступен на http://localhost:3000.
Не перезаписывайте существующий `.env`. Flyway выполняет миграции при старте:
существующая БД требует отдельной проверки и резервной копии. Остановка без удаления
данных: `docker compose down`. Не используйте `down -v` для рабочей базы.

Настройки ML/OpenRouter перечислены в `.env.example`; настоящий ключ хранится
только в локальном `.env`. Наличие ML-модуля не означает готовность backend API генерации.
Открытые тестовые пароли в `.env.ci.example` предназначены только для одноразового CI.
Старые переменные `MINIO_ACCESS_KEY`/`MINIO_SECRET_KEY` замените в локальном окружении
на `S3_ACCESS_KEY`/`S3_SECRET_KEY`; автоматического выбора запасных ключей больше нет.
Для Compose из каталога backend передавайте корневой env-файл явно:
`docker compose --env-file ../.env up -d --build --wait`.
Перед публичным стендом нужны отдельные секреты, закрытые БД/S3, резервные копии и откат.
Номера портов не являются секретами; доступ ограничивается сетью и настройками публикации.
Google Fonts скачивает браузер: сборка шрифты не загружает и локально их не хранит.

### Как работают проверки

Сфера — основной репозиторий, PR и слияния выполняются там. GitHub Actions запускает
проверки при push. Сначала Gitleaks проверяет историю на секреты, затем `ci/changes.mjs`
выбирает задания. Его правила проверяет `node --test ci/changes.test.mjs`.
Все вспомогательные проверки используют Node.js 24 без дополнительных пакетов.

| Изменение | Проверки |
| --- | --- |
| Только README в feature-ветке | Поиск секретов и выбор этапов |
| Только код frontend или backend в feature-ветке | Тесты и сборка соответствующего компонента |
| Compose, Dockerfile, контракт API, CI или неизвестные пути | Оба компонента, Compose и smoke |
| Браузерные тесты | Оба компонента, Compose, smoke и браузер |
| Push в `dev` | Оба компонента, Compose и smoke |
| Push в `master` | Оба компонента, Compose, smoke и браузер |

Сборки frontend и backend идут параллельно. Готовые Angular-файлы и JAR передаются
как артефакты того же запуска; Docker упаковывает их без повторной компиляции.
`compose.ci.yml` дополняет основной Compose: отдельное имя проекта, одноразовые данные
в tmpfs, закрытые порты БД/S3/backend. После готовности сервисов `ci/smoke.mjs` проверяет
интерфейс, запрет гостевого доступа, регистрацию, вход, загрузку, скачивание и удаление файла.
Тесты backend используют отдельный PostgreSQL и переменные `TEST_DATABASE_URL`,
`TEST_DATABASE_USERNAME`, `TEST_DATABASE_PASSWORD`, а не рабочую БД.
Отчёты тестов хранятся 7 дней, готовые сборки — 1 день. Контейнеры удаляются и при ошибке.

Полная ручная проверка: **Actions → Проверка проекта → Run workflow**,
выбрать ветку, включить `full`, выключить `negative_smoke`. Ручной запуск не публикует образы.
`negative_smoke` намеренно задаёт неверный адрес API: ожидается красный результат,
чтобы проверить, что CI обнаруживает поломку. Не включайте его при приёмке.
Smoke создаёт тестовые данные — не запускайте его против рабочего стенда.

`packages: write`; вход выполняется временным `GITHUB_TOKEN` без личного токена.

После принятия PR в Сфере передайте точный коммит в GitHub:

```bash
git fetch origin
git push github origin/dev:refs/heads/dev
```

После релизного слияния аналогично передаётся `origin/master:refs/heads/master`.
Не используйте force-push. Два remote сами по себе не обеспечивают синхронизацию.

Для запуска опубликованных образов на новой копии с новой БД, после подготовки `.env`:

```bash
export IMAGE_TAG=sha-<полный-SHA>
docker compose -f docker-compose.yml -f compose.registry.yml pull
docker compose -f docker-compose.yml -f compose.registry.yml up -d --no-build --wait
```

В PowerShell задайте переменную как `$env:IMAGE_TAG = 'sha-<полный-SHA>'`.
Это локальный запуск образов, готовый deployment здесь ещё не настроен.
Для приёмки нужны PR в Сфере, человеческий аппрув и комментарий ревьюера,
зелёный CI принятого коммита и проверка после слияния. Затем удаляется feature-ветка.

## Генерация и таблица тестов — реальные API (TY5 / 62, 65, 66, 75)

Используются существующие макеты «TY5 / Единый стиль». Параметры и defaults загружаются
из `GET /api/generation/parameters`, запуск — `POST /api/quizzes` с `Idempotency-Key`,
состояние — `GET /api/generation-jobs/{id}` раз в две секунды (разрешённый fallback
контракта). Проценты не вычисляются. Таблица читает собственные записи через
`GET /api/quizzes`; демонстрационных строк и кнопок результата в обычном приложении нет.

### Первоначальная настройка

Нужны Git, Docker Desktop с Linux-контейнерами и Docker Compose. В новой копии проекта
с новой БД создайте `.env` из `.env.example` и заполните обязательные пароли/JWT/S3
по разделу «Запуск и CI». Для реальной модели задайте `OPENROUTER_API_KEY` и
`OPENROUTER_MODEL=nvidia/nemotron-3.5-super-vl:free`; ключ передаётся только backend.
Переменные уже описаны в `.env.example`, новых переменных frontend нет.
Не коммитьте `.env` и не публикуйте полный вывод конфигурации Docker.

Первый запуск: `docker compose up --build`, дальнейший — `docker compose up`.
Дождитесь здорового backend и откройте `http://localhost:3000`. При конфликте портов
задайте предусмотренные переменные `*_PORT`. Старую экспериментальную БД не подключайте:
при старте применяются принятые миграции V1/V2/V3/V4/V6/V7; volumes с данными не удаляйте.
Подробности реального ML и ограничения файлов: [backend/GENERATION.md](backend/GENERATION.md).

### Что проверить через интерфейс

1. Зарегистрируйте тестовый аккаунт либо войдите. Для гостя `/tests` открывает вход,
   после авторизации — собственные тесты. Новый аккаунт видит пустой список.
2. На главной «Создать тест» открывает материалы; «Начать тренировку» — тесты.
   Загрузите небольшой UTF-8 TXT/PDF/DOCX и нажмите «Создать тест» у нужного документа.
3. Сверьте название, формат и размер материала. Укажите название теста (1–100 символов
   после trim), выберите 5/10 вопросов, сложность и ровно один доступный тип.
   Defaults и доступность определяет серверный справочник.
4. Запустите генерацию. Повторное нажатие во время отправки заблокировано. При неизвестном
   исходе отправки повтор с теми же данными использует прежний ключ, включая reload вкладки.
   Осознанная новая попытка после терминального FAILED получает новый ключ.
5. В ожидании показывается реальный этап без процентов и кнопки возврата к настройкам.
   Обновление страницы или возвращение к тому же материалу продолжает чтение принятой
   задачи в этой вкладке, без повторного POST. При 401 опрос останавливается, доступен повторный вход с возвратом к той же генерации.
   Временная ошибка чтения статуса/списка оставляет ожидание и понятное сообщение, проверка продолжается.
6. Готовность появляется только после COMPLETED с quizId и повторного чтения положительного
   числа вопросов из собственного списка. Проверьте фактическое количество.
   «К готовому тесту» открывает таблицу с выделенной созданной строкой. После reload
   запись остаётся: это чтение backend, а не сохранение примера в браузере.
7. Реальная терминальная ошибка показывает общую форму без внутренних исключений.
   «К настройкам» сохраняет материал, название и параметры; «Повторить генерацию»
   отправляет их заново. Ошибка валидации до POST остаётся у формы.
   Без ключа модели можно проверить настоящий негативный путь NOT_CONFIGURED;
   отсутствие ключа не подтверждает успешную генерацию.
8. Таблица: поиск по названию без учёта регистра, сортировка по названию/материалу/дате
   в обе стороны, стабильный порядок равных значений. ID скрыт и не сортируется.
   Проверьте пустой список, ошибку API/повтор, экран 390 px и выход из аккаунта.

Переименование №77 и удаление №76 пока недоступны для реальных строк: принятый backend
не реализует эти операции. Старые демонстрационные провайдеры оставлены для unit-тестов,
но не подменяют настоящий список. Прохождение, оценка и персонализация в объём не входят.

Список API не раскрывает вопросы/ответы. Для ручной проверки JSON уже сохранённого теста
на своём изолированном стенде можно прочитать `quizzes.result_json` по полученному quizId;
это диагностический экспорт, не новый публичный endpoint и не экран прохождения.
Не передавайте токены или provider key вместе с результатом.

### Локальные проверки и приёмка

После `npm --prefix frontend ci` выполните:
`npm --prefix frontend run test -- --watch=false` и `npm --prefix frontend run build`.
На 03.11.2026 прошли 125 тестов и production-сборка; backend из e5f98eb собран в bootJar.
Реальный браузерный негативный путь проверен с новой отдельной БД: регистрация,
загрузка TXT, параметры SQL, POST202, FAILED, возврат/повтор и отсутствие несохранённого
теста в списке после reload. Успешный путь с внешней моделью в этой FE-ветке пока ждёт
ключа и ручной проверки. Локальные результаты не являются зелёным CI.
Для полного Done нужны подтверждённый успешный FE/BE/ML-сценарий, независимое повторение,
PR в карточках, человеческое ревью и актуальный CI. Новые проверки/ограничения фиксируются
в [отчёте интеграции frontend](docs/frontend-generation-integration.md).

## Как проверить задачу «API параметров генерации»

В PowerShell из корня репозитория:

```powershell
$base = 'http://localhost:8080'
$suffix = [guid]::NewGuid().ToString('N').Substring(0, 8)
$registration = @{username="student_$suffix"; email="student_$suffix@example.test"; password='local-password-123'} | ConvertTo-Json
$auth = Invoke-RestMethod "$base/api/auth/register" -Method Post -ContentType 'application/json' -Body $registration
$headers = @{Authorization="Bearer $($auth.token)"}
$params = Invoke-RestMethod "$base/api/generation/parameters" -Headers $headers
$params | ConvertTo-Json -Depth 6
```

Ожидается HTTP 200: `questionCounts` со значениями 5/10, три `difficulties`, три
`questionTypes`, `available` у каждого значения, `defaults` из БД и
`questionTypeSelection: SINGLE`. Начальные доступности — true. Defaults подтверждены пользователем 03.11.2026:
10 / MEDIUM / SINGLE_CHOICE.
Без токена — HTTP 401. Ответ имеет Cache-Control: no-store.

Проверка запрета 20 вопросов (PowerShell покажет HTTP 400):

```powershell
$headers['Idempotency-Key'] = [guid]::NewGuid().ToString()
$body = @{materialId=[guid]::NewGuid().ToString(); questionCount=20; difficulty='MEDIUM'; questionType='SINGLE_CHOICE'} | ConvertTo-Json
Invoke-RestMethod "$base/api/quizzes" -Method Post -Headers $headers -ContentType 'application/json' -Body $body
```

В текущем dev POST с допустимыми настройками возвращает 202 с ID фоновой задачи,
а ошибки справочника отклоняются до запуска ML. Frontend использует реальные
параметры/defaults, очередь и статус; подробный сценарий — в разделе выше.
Ровно один тип передаётся строкой `questionType`; массив типов, темы и персонализация
не входят в текущий объём.

Изменение доступности/defaults и повторная проверка по шагам:

## Сборка и проверки

Unit-тесты используют mock зависимостей. Spring/JDBC-тесты используют отдельный
PostgreSQL с профилем test, как в CI; прежнюю пользовательскую БД указывать нельзя.
Для локального запуска создайте одноразовый контейнер (порт 55432 должен быть свободен):

```powershell
docker run -d --name generation-unit-db -e POSTGRES_DB=generation_test -e POSTGRES_USER=generation_test -e POSTGRES_PASSWORD=integration-only-password -p 127.0.0.1:55432:5432 postgres:16-alpine
docker exec generation-unit-db pg_isready -U generation_test -d generation_test
$env:TEST_DATABASE_URL = 'jdbc:postgresql://127.0.0.1:55432/generation_test'
$env:TEST_DATABASE_USERNAME = 'generation_test'
$env:TEST_DATABASE_PASSWORD = 'integration-only-password'
cd backend
.\gradlew.bat build
python scripts/check-generation-parameters.py
# После проверок удалить только созданный проверочный контейнер:
docker rm -f -v generation-unit-db
```

Перед build дождитесь `accepting connections` от pg_isready. Если контейнер с таким
именем уже существует, выберите другое имя или используйте свой отдельный тестовый
PostgreSQL. В Linux/CI задайте те же TEST_DATABASE_* и выполните `./gradlew build`.
`build` включает валидацию OpenAPI, генерацию Java, все тесты и сборку jar.

Unit-тесты новой логики и HTTP-контракт без запуска БД:

```powershell
.\gradlew.bat test --tests 'tech.genna.TY3.service.generation.GenerationParametersServiceTest' --tests 'tech.genna.TY3.controller.GenerationParametersControllerTest'
```

Python-сценарий поднимает отдельные PostgreSQL 16 и backend на 127.0.0.1:18080,
проверяет настоящие HTTP-запросы, сохранённые изменения справочника, отклонение
запрещённых параметров и неизменность снимка. После проверки удаляет только свои
контейнеры/тома. При занятом порте задайте GENERATION_TEST_PORT=18081 в окружении.
Используется уже собранный `backend/build/libs/app.jar`; корневой Compose и его БД
не затрагиваются. Результаты Gradle: `backend/build/reports/tests/test/index.html`.

## TY5: backend генерации теста (BE-60 / ML-64)

Тестировщику: [безопасная настройка ключа и проверка генерации через API](docs/ml-api-testing.md).
В инструкции разделены локальный запуск и общий учебный сервер. Ключ модели передаётся
только backend через env; тестировщик общего стенда использует собственный JWT.
Для серверного запуска нужен опубликованный SHA-тег с ML, а не старый образ первого релиза.

Backend принимает параметры и возвращает `202` с ID задачи. Извлечение PDF/DOCX/TXT,
реальный вызов `QuizGenerator.generate`, проверка и сохранение выполняются в фоне.
HTTP-снимок и WebSocket доступны владельцу задачи; `COMPLETED` с `quizId` выставляется
только после записи теста. Повтор с тем же ключом идемпотентности не создаёт дубль.

Для запуска сначала заполните обязательные секреты `.env` по инструкции выше.
Для настоящей модели дополнительно задайте `OPENROUTER_API_KEY` и
`OPENROUTER_MODEL=nvidia/nemotron-3.5-super-vl:free`. Ключ остаётся на сервере.
Платных запасных моделей нет; ошибки бесплатного провайдера не означают готовый тест.

Контракт, пример запуска и проверки: [backend/GENERATION.md](backend/GENERATION.md).
Метод ML, M1 v2, промпты и ограничения: [backend/ML.md](backend/ML.md).
Реальное сохранение TXT подтверждено на `0346e02`; ограничения и результаты:
[отчёт приёмки](docs/generation-readiness-2026-11-03.md).
Локальные проверки не заменяют CI, человеческое ревью и повтор другим участником.

Для ручного ML-прогона: `./scripts/ml-live.ps1 -Type single_choice -Count 5 -Difficulty medium -Model nvidia/nemotron-3.5-super-vl:free`.
Ключ читается из окружения либо локального игнорируемого `.env.ml.local`; при отсутствии
предлагается скрытый ввод с локальным сохранением. Файл не публиковать.
`ML_LIVE_MATERIAL_PATH` — путь только локального тестового инструмента, не параметр API.
