# Публикация frontend-задач

Согласованный процесс: feature-ветки от актуального dev, PR в dev. Переход dev → master
согласуется отдельно. Постоянную ветку frontend и цепочку зависимых веток не создаём.
Заглушки допустимы в принимаемом прототипе, но не закрывают требования реального API.

Коммиты — Conventional Commits, описание на русском: `feat: добавить ...`,
`fix: исправить ...`, `docs: описать ...`, `test: проверить ...`.
Имя feature-ветки содержит ключ задачи. Одна задача — одна короткая ветка.

## Что готовим перед PR

Ключ и точное название задачи; source/target ветки; название PR; описание проблемы и
результата; границы заглушек; инструкцию приёмки; результаты тестов/сборки; актуальные
скриншоты; список оставшихся AC/DoD. Не считать название нового теста реализацией
отдельной задачи переименования существующего теста.

## Текущая задача62: публикация

Команды ниже выполняются пользователем из корня репозитория. Перед каждой следующей
командой проверить успех предыдущей; при ошибке остановиться. Push/merge агент выполняет
только по отдельному разрешению. Перед публикацией обновить результаты проверок,
если после последнего прогона менялся код.

```powershell
git branch --show-current
git status --short
git fetch origin --prune
git log --oneline HEAD..origin/dev
```

Ожидаемая ветка: `feature/tpivt6_26-62-generation-settings`. Если dev продвинулся,
сначала сохранить свои изменения коммитом, затем согласовать обновление feature-ветки
из origin/dev, разрешить конфликты и повторить тесты. Не выполнять reset --hard/clean.

Выборочно добавить только нужные файлы:

```powershell
git add README.md frontend/src/app/app.routes.ts frontend/src/app/features/materials/materials.html frontend/src/app/features/materials/materials.ts frontend/src/app/features/generation/ docs/frontend-delivery.md
git diff --cached --stat
git diff --cached
git diff --cached --check
git commit -m "feat: добавить прототип настройки генерации теста"
git show --stat --oneline HEAD
git push -u origin feature/tpivt6_26-62-generation-settings
```

Локальные .gitignore, AGENTS.md, tools, docs/workflows, .env и docker-compose.local.yml
не добавлять в этот коммит. Проверить staged diff на посторонние изменения и секреты.
Если нужные файлы уже закоммичены, второй такой же коммит не создавать.

В Сфера.Код создать PR: source — эта feature-ветка, target — dev. Вставить описание,
приложить скриншоты, запросить ревью другого участника. PR не отправлять в master.
Не использовать автоматическое закрытие карточки62: интеграция ещё не выполнена.

## После подтверждённого merge в dev

```powershell
git status --short
git fetch origin --prune
git switch dev
git pull --ff-only origin dev
git rev-parse HEAD
git rev-parse origin/dev
```

HEAD и origin/dev должны совпасть. Если переключение блокируют локальные файлы,
остановиться и сохранить их отдельно; не удалять и не сбрасывать их. При отказе
fast-forward выяснить расхождение, не выполнять принудительный reset.
Проверить в dev изменения PR, выполнить тесты/сборку и повторить сценарий приёмки.
Docker сам не обновляется при переключении Git: отдельно пересобрать frontend
по конфигурации своего стенда; backend/БД без необходимости не перезапускать.

Только после подтверждения результата удалить завершённую feature-ветку. После Squash
`git branch -d` может отказать: сначала проверить содержимое принятого PR и отсутствие
неопубликованных изменений, затем отдельно удалить локальную ветку. Удаление удалённой
ветки — через интерфейс принятого PR либо явно согласованной командой. Чужие ветки
не удалять. Новую задачу начинать от обновлённого dev.

## Перед закрытием задачи

Ссылка PR в артефактах; человеческий аппрув; комментарий ревьюера «Ревью пройдено»
со ссылкой; применимый зелёный CI со ссылкой; merge; итоговая проверка; удалить ветку.
Результаты локальных проверок обозначать локальными. Доступность backend, проверка
сохранения после обновления страницы и другие интеграционные AC обязательны,
если входят в карточку. При отсутствии CI действовать по согласованному DoD карточки,
явно фиксируя невыполненные пункты общих требований проекта.
