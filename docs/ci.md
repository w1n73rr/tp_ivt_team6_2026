# CI: сборка, тесты и отдельный Compose

Перед остальными заданиями на каждом запуске обязательна проверка истории Gitleaks.
Она действует и для README-only push. [Проверки безопасности и ограничения](security-readiness.md).

Публикация проверенных образов и запуск без компиляции: [реестр GHCR](registry.md).

Сфера — основной репозиторий для PR и слияний. GitHub запускает `.github/workflows/ci.yml`
при push любой ветки, содержащей workflow. Ветки на обоих серверах должны указывать
на один коммит. PR только в Сфере не создаёт событие GitHub `pull_request`.

## Что проверяется

1. `frontend`: Node.js24, `npm ci`, все Angular/Vitest-тесты, production-сборка.
2. `backend`: JDK25, Gradle Wrapper9.1, unit/контрактные/API-тесты и `bootJar`.
   Для API-тестов GitHub создаёт отдельный PostgreSQL16. Профиль `test` не читает
   `.env` и требует `TEST_DATABASE_URL`, `TEST_DATABASE_USERNAME`, `TEST_DATABASE_PASSWORD`.
   Файловое хранилище в этих тестах заменено Mockito, реальное S3 проверяется ниже.
3. `integration`: готовые JAR и Angular-файлы передаются из первых двух заданий
   через артефакты этого же прогона. Docker собирает только runtime-слои, без повторной
   компиляции приложения (target `ci-runtime`). Затем запускаются
   PostgreSQL, SeaweedFS, backend и nginx/frontend. Ожидаются healthcheck, выполняются
   `ci/smoke.py` через nginx. Существующие Selenide UI-тесты без окна Chrome запускаются
   автоматически для релизного `master`, а также вручную с параметром `full=true`.
   На `dev` обязательны оба компонента, Compose и smoke, без браузерного набора.

Перед заданиями `ci/changes.py` сравнивает все коммиты отправки, включая удаления
и переименования. На feature-ветке изменения только frontend/backend запускают
лишь тесты и сборку соответствующего компонента, без Compose. README и docs — только
лёгкий этап выбора. Compose, Dockerfile, общий API-контракт, CI и неизвестные пути
запускают оба компонента и интеграцию; изменения ui-tests — также браузерный набор.
На первом push сравнивается вклад ветки относительно dev; при недоступной базе
включается расширенная проверка. Ручной запуск всегда включает интеграцию.

В Actions → «Проверка проекта» → Run workflow выберите нужную ветку.
Параметр «Полный прогон» включает браузерные проверки. «Контрольный красный прогон»
намеренно направляет smoke на неверный путь: шаг обязан упасть, а отчёты/логи
и очистка контейнеров — выполниться. По умолчанию этот параметр выключен.
Готовые сборки хранятся1день. Docker-кеш раздельный для сервера и интерфейса.
Локальный `docker compose build` по-прежнему собирает исходники обычным способом.

Smoke проверяет выдачу Angular, отказ гостю, регистрацию и вход, отказ с неверным
паролем, список материалов, загрузку TXT, точное совпадение скачанных байтов,
удаление и последующий404. Это не полное покрытие всех функций продукта.

JUnit/HTML-отчёты сохраняются в Actions Artifacts на7дней даже при ошибке.
При сбое интеграции печатается хвост логов сервисов с тестовыми данными.
Ни токены, ни тела ответов smoke не печатает. Обычные push не получают секретов деплоя.
Зависимости Actions закреплены на commit SHA; их обновляют отдельным ревью.

## Локальный запуск на новой БД

Нужны Docker Compose >=2.24.4, JDK25, Python3 и Chrome для UI-тестов.
В PowerShell из корня проекта:

```powershell
docker compose --env-file .env.ci.example -p tpivt-ci85 -f docker-compose.yml -f compose.ci.yml build
docker compose --env-file .env.ci.example -p tpivt-ci85 -f docker-compose.yml -f compose.ci.yml up -d --no-build --wait --wait-timeout 240
python ci/smoke.py --base-url http://localhost:18085
./backend/gradlew.bat -p ui-tests test '-Dui.headless=true' '-Dui.baseUrl=http://localhost:18085' --no-daemon
docker compose --env-file .env.ci.example -p tpivt-ci85 -f docker-compose.yml -f compose.ci.yml down --remove-orphans
```

Используется порт18085. Укажите другой `FRONTEND_PORT` в окружении, если он занят,
и передайте тот же адрес smoke/UI. CORS в Compose следует за портом frontend.
Всегда используйте отдельное имя проекта и оба файла Compose с явным env-файлом.
Конфигурация CI хранит PostgreSQL и S3 в tmpfs: удаление контейнеров теряет эти
тестовые данные. Основные volumes не подключаются и не удаляются.
Не запускайте CI-команды против существующего стенда или старой БД.

Для backend API-тестов отдельно создайте одноразовый PostgreSQL. Укажите его JDBC URL
и учётные данные через три `TEST_DATABASE_*`, затем запустите
`./backend/gradlew.bat -p backend test --no-daemon`. Без этих параметров API-тесты
должны завершиться ошибкой, а не подключиться к рабочей БД. Unit-тесты без Spring
можно запускать выборочно без БД. Профиль `test` нельзя использовать для деплоя.

## Обычный локальный запуск и граница деплоя

Скопируйте `.env.example` в `.env` только если локального файла ещё нет.
Локальные значения предназначены для разработки. Для новой копии/новой БД:
`docker compose up -d --build --wait`. Повторный запуск без изменения кода:
`docker compose up -d --wait`. Flyway выполняет миграции при старте backend;
на существующей БД сначала требуется отдельное согласование и резервная копия.

Фиксированные `container_name` убраны; имена и volumes изолируются именем Compose-проекта.
Порты привязаны к127.0.0.1, чтобы локальная БД и S3 не открывались в сеть.
Не меняйте имя существующего Compose-проекта без проверки того, какие volumes он использует.

Google Fonts остаются внешними: `optimization.fonts.inline=false` отключает их загрузку
при сборке. Браузер получает их сам; без доступа к Google возможен запасной шрифт
или отсутствие символьных иконок. Шрифты локально не сохраняются.

Публикации образов и deployment здесь нет. Для стенда потребуются отдельные секреты,
защищённая ветка релиза, HTTPS, резервное копирование и план отката.
Принятие задачи: ссылка PR, человеческое ревью/аппрув, ссылка CI для фактического SHA,
слияние в Сфере, проверка принятого коммита, затем удаление feature-ветки.
