# Реестр образов GHCR

Пакеты проекта:
- `ghcr.io/w1n73rr/tp_ivt_team6_2026-backend`
- `ghcr.io/w1n73rr/tp_ivt_team6_2026-frontend`

Публикация разрешена только после успешного задания «Проверка всего приложения».
На push в `dev`/`master` она автоматическая. Для начальной публикации из ветки85:
Actions → «Проверка проекта» → Run workflow → выбрать ветку85, включить
«Полный прогон» и «Опубликовать проверенные образы», контрольную ошибку оставить выключенной.
Обычные feature-push ничего в реестр не публикуют.

Каждый пакет получает тег `sha-<полный SHA>`. Принятые `dev` и `master` дополнительно
получают одноимённые подвижные теги. Тега `latest` нет. Для воспроизводимого запуска
используйте SHA-тег или digest. Приложение не компилируется повторно: публикуются
runtime-образы из артефактов того же проверенного прогона.

GitHub Actions использует временный `GITHUB_TOKEN`; `packages: write` выдан только
заданию публикации. Личный токен в Secrets добавлять не требуется.
При первой публикации GHCR создаёт приватные пакеты. По решению команды оба пакета
нужно сделать публичными: профиль владельца → Packages → пакет → Package settings →
Change visibility → Public. Это отдельная настройка от публичности Git-репозитория.

Для новой копии с новой БД скопируйте `.env.example` в `.env` (не перезаписывайте
существующий файл), задайте `IMAGE_TAG=sha-<проверенный SHA>` в окружении и используйте
`docker-compose.yml` вместе с `compose.registry.yml`: сначала `pull`, затем
`up -d --no-build --wait`. Файл registry не отключает Flyway; не запускайте его
на старой БД без отдельного согласования. Это пока локальный запуск, не deployment.

Слияния выполняются в Сфере. После Squash получите принятый коммит и отправьте его
в GitHub, например `git fetch origin`, затем `git push github origin/dev:refs/heads/dev`.
Для релиза аналогично с `master`. Не используйте force-push. Два сервера не синхронизируются
от самого наличия remote; локальный hook не замечает серверный merge в Сфере.
