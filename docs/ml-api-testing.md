# Проверка генерации тестов через API

Проверяем BE-60 и ML-64 из dev, начиная с 682d97a. Слияние проверено сравнением содержимого с a69d179: деревья одинаковы. Полный локальный clean test bootJar на новой PostgreSQL ранее прошёл: 106 тестов, один opt-in live-тест пропущен. Это не ссылка на зелёный CI. Реальный TXT-сценарий с моделью, записью и WebSocket подтверждён, но стабильность провайдера и качество всех сложностей не гарантированы.

## Два разных ключа

- OPENROUTER_API_KEY даёт backend доступ к модели. Он хранится только на стороне сервера. Не вставляйте его в Swagger, Authorization приложения, браузер, issue, PR, скриншоты или логи.
- JWT приложения получается при регистрации/входе тестового пользователя. Именно его используйте как Bearer в запросах к нашему API. Получайте отдельный JWT для каждой проверяемой учётной записи.

На общем стенде тестировщику не нужен ключ OpenRouter: его уже должен настроить обслуживающий backend участник. Нужны адрес стенда и собственная тестовая учётная запись. Если backend без provider key, ожидается FAILED / NOT_CONFIGURED, это не проверка настоящей генерации.

Для собственного стенда используйте отдельный provider key, полученный по закрытому каналу либо созданный в своём аккаунте. Сам ключ в этой инструкции отсутствует. Текущий клиент разрешает только явные :free-модели и не включает платный fallback.

## Общий учебный сервер

Эту часть выполняет обслуживающий сервер участник; тестировщик настраивает provider key только если сам поднимает backend. Отправляйте выделенный тестовый ключ лично, не пересылайте авторский .env целиком.

Подключение к текущей ВМ:

```bash
ssh -i ~/.ssh/id_ed25519 deploy@84.54.56.192
```

В /opt/tpivt используйте основной docker-compose.yml, compose.registry.yml и compose.server.yml из одной принятой версии. Условия первого запуска и четыре обязательных секрета описаны в корневом README. В существующем локальном серверном .env укажите через редактор, без ключа в командной строке:

```dotenv
OPENROUTER_API_KEY=<выделенный тестовый ключ, только в настоящем .env>
OPENROUTER_MODEL=nvidia/nemotron-3.5-super-vl:free
OPENROUTER_REASONING_ENABLED=false
GENERATION_WORKERS=1
SERVER_ORIGIN=http://84.54.56.192
IMAGE_TAG=sha-<проверенный и опубликованный SHA с BE-60 и ML>
```

GENERATION_WORKERS=1 ограничивает одновременные генерации для слабой ВМ; остальные принятые задачи ждут в PostgreSQL. Локальная модель/GPU не нужны. Это стартовая настройка, её достаточность под нагрузкой ещё нужно измерить.

Не копируйте IMAGE_TAG из примера буквально. Нужен реально опубликованный парный тег frontend/backend из зелёного CI, содержащий изменения dev 682d97a или более поздние. Старый первый релиз sha-a22830c... из README не подтверждает наличие ML. Push в Сферу сам по себе не публикует образы GHCR и не развёртывает сервер. Пока подходящего тега нет, используйте отдельный локальный стенд из следующего раздела; не подменяйте проверку принятых изменений старым образом.

После выбора реального тега:

```bash
cd /opt/tpivt
chmod 600 .env
sudo docker compose --env-file .env -f docker-compose.yml -f compose.registry.yml -f compose.server.yml config --quiet
sudo docker compose --env-file .env -f docker-compose.yml -f compose.registry.yml -f compose.server.yml pull
sudo docker compose --env-file .env -f docker-compose.yml -f compose.registry.yml -f compose.server.yml up -d --no-build --wait --wait-timeout 300
sudo docker compose --env-file .env -f docker-compose.yml -f compose.registry.yml -f compose.server.yml ps
```

Ключ читается основным Compose из серверного .env и передаётся только backend; менять Dockerfile или собирать образ с ключом не нужно. После изменения .env повторите up: обычный restart не применяет новое окружение контейнера. Не публикуйте config без --quiet или docker inspect. Не меняйте существующие пароли БД/S3 ради этого шага.

Для первого совместного прогона нужна новая БД или БД, совместимая с принятой dev-цепочкой V1/V2/V3/V4/V6/V7. Экспериментальные БД со старой V4 задач и V5 статусов не подключать; автоматический repair/удаление volumes не предусмотрены. Перед обновлением сервера с данными согласуйте резервное копирование и миграции; эта инструкция не выполняет обновление автоматически.

После healthcheck обслуживающий сервер участник передаёт тестировщику адрес и SHA. На текущем сервере наружу опубликован nginx:80, backend не обязан слушать публичный :8080. Проверяйте API по адресу http://84.54.56.192/api/... через nginx. Работайте с отдельными тестовыми аккаунтами и материалами. Автоматический smoke ниже запускайте на одноразовом локальном стенде, а не на сервере с пользовательскими данными.

## Собственный локальный стенд

1. Получите актуальный dev; для воспроизводимого сравнения запишите git rev-parse HEAD. Не запускайте прежнюю БД экспериментальной BE-60 с другими V4/V5. Используйте новый Compose-проект и новые volumes; старые пользовательские данные не удаляйте.
2. По корневому README создайте .env из .env.example. Заполните независимыми случайными значениями POSTGRES_PASSWORD, JWT_SECRET, S3_ACCESS_KEY и S3_SECRET_KEY. Это обязательно, значения шаблона пустые.
3. Укажите OPENROUTER_MODEL=nvidia/nemotron-3.5-super-vl:free. По умолчанию reasoning выключен. Ключ можно записать в игнорируемый корневой .env либо передать скрытым вводом в окружение процесса, как ниже. .env.ml.local используется ручным ML-скриптом и автоматически не является env-файлом Docker Compose.
4. Убедитесь, что Docker работает и локальные порты 3000/8080/5432/8333 свободны; при необходимости настройте *_PORT в .env.

PowerShell 7: ключ не попадает в текст команды и не выводится. Запустите из корня репозитория:

```powershell
$secret = Read-Host 'Ключ OpenRouter (ввод скрыт)' -AsSecureString
try {
    $env:OPENROUTER_API_KEY = [Net.NetworkCredential]::new('', $secret).Password
    docker compose -p ml-acceptance up --build
} finally {
    Remove-Item Env:OPENROUTER_API_KEY -ErrorAction SilentlyContinue
    $secret.Dispose()
}
```

Команда работает в переднем плане. Дождитесь healthy; используйте второе окно терминала для API-проверок. После остановки окружение этого процесса очищается. Ключ всё равно доступен обслуживающему Docker администратору в конфигурации работающего контейнера — не публикуйте docker inspect и docker compose config. Остановка без удаления данных: docker compose -p ml-acceptance down. Не используйте down -v для пользовательских БД.

## Быстрый автоматизированный сценарий API

Нужен Node.js 24+ только для проверочного клиента, не для работы backend. Из второго окна в корне репозитория:

```powershell
node ci/generation-check.mjs --base-url http://localhost:8080 --file backend/src/test/resources/ml/demo-lecture.txt
```

Для реального материала замените --file на путь к своему PDF/DOCX/UTF-8 TXT. Путь используется только локальным тестовым клиентом: он загружает байты через API, production-генератор не получает путь.

Клиент сам регистрирует тестовые аккаунты, загружает файл, запускает 5 MEDIUM SINGLE_CHOICE, проверяет 202, идемпотентность, конфликт, права владельца, терминальный статус и наличие одной записи в реальном списке. JWT и provider key не печатает. Сохраняет тестовые записи на стенде. PASS этого сценария не подтверждает качество hard, все типы или WebSocket. Маленькая demo-lecture.txt — только smoke-материал.

Без provider key отдельный негативный сценарий:

```powershell
node ci/generation-check.mjs --base-url http://localhost:8080 --expect-unconfigured
```

Он ожидает NOT_CONFIGURED и отсутствие сохранённого теста; не выдавайте его за реальную генерацию.

## Ручная проверка разных настроек

1. Локально откройте http://localhost:8080/swagger-ui.html. На общем сервере используйте Postman или другой HTTP-клиент: текущий nginx публикует /api, но не Swagger. Зарегистрируйтесь POST /api/auth/register либо войдите POST /api/auth/login. В заголовке Authorization используйте Bearer JWT тестового пользователя; в Swagger локально — Authorize (Bearer), не provider key.
2. GET /api/generation/parameters: проверьте доступность и defaults. Начальный справочник: 5/10, EASY/MEDIUM/HARD, три типа; defaults — 10, MEDIUM, SINGLE_CHOICE.
3. POST /api/materials: multipart metadata с name и subjectName (часть с Content-Type application/json), файл в поле file. Сохраните material.id из ответа. Материал должен принадлежать вошедшему пользователю.
4. POST /api/quizzes: в заголовке Idempotency-Key задайте новый UUID, в теле передайте пример ниже. Используется один questionType, не массив questionTypes.

```json
{
  "materialId": "UUID загруженного собственного материала",
  "name": "Проверка генерации",
  "questionCount": 5,
  "difficulty": "MEDIUM",
  "questionType": "SINGLE_CHOICE"
}
```

5. Ожидается быстрый 202, id задачи и Location. Это принятие задачи, не готовый тест.
6. GET /api/generation-jobs/{id}: опрашивайте примерно раз в 2 секунды до COMPLETED либо FAILED. Фоновые этапы уточняют RUNNING и не являются процентами. Общий лимит включает файл, модель и проверку; обычные параметры — 90 секунд на обращение и 240 секунд на ML-цикл.
7. Только COMPLETED с quizId означает подтверждённую запись. GET /api/quizzes должен вернуть соответствующий тест в items и фактическое число вопросов; повторите GET, результат должен сохраниться. Список не раскрывает правильные ответы.
8. Повторите тот же POST с тем же ключом и телом — ожидается тот же id, без второго теста. То же значение ключа с другим количеством — 409. Для осознанного нового запуска создайте новый ключ.

Повторите настройки с 10 вопросами, MULTIPLE_CHOICE и TRUE_FALSE и разными сложностями. SINGLE_CHOICE — четыре варианта/один правильный; MULTIPLE_CHOICE — четыре/два или три; TRUE_FALSE — два/один. Ключи и содержание проверяются отдельно в приватном результате ML: публичный список специально их не отдаёт. Формальная схема: backend/src/main/resources/ml/result-v2.schema.json; примеры: docs/ml-examples.

Для WebSocket используйте контракт backend/GENERATION.md: /api/ws/generation, разрешённый Origin, один кадр SUBSCRIBE с JWT и jobId. JWT нельзя помещать в URL. Проверяйте версии, повторное подключение, терминальный статус и отказ чужой подписке. WebSocket не запускает модель заново.

## Ошибки и качество

- Без JWT — 401; чужая задача — 404. Неверные настройки — 400, ML не запускается.
- Пустой скан — DOCUMENT_NO_TEXT; защищённый документ — DOCUMENT_PROTECTED; неразбираемый — DOCUMENT_UNREADABLE. Ограничения: 10 МБ, до 10 страниц PDF, до 30 000 извлечённых символов; oversized-документ не обязан успешно генерироваться.
- RATE_LIMITED, MODEL_UNAVAILABLE и MODEL_TIMEOUT — реальные отказы провайдера. INVALID_MODEL_OUTPUT — некорректный ответ; QUALITY_REJECTED — кандидат отклонён проверкой содержания. При FAILED тест не должен появляться как готовый. Сырые ответы провайдера и секреты в пользовательскую ошибку не попадают.
- Проверяющая модель может пропустить дубли и слишком лёгкие вопросы. Для medium проверяйте различение/применение; для hard — совместное применение нескольких правил. Длинная фраза сама по себе не сложность. Оцените каждый правильный ответ и непомеченные варианты по источнику. Примеры успешных ответов не доказывают стабильность серии.

## Что приложить к отчёту

SHA, дата, окружение, формат и размер материала, настройки, jobId, итоговый безопасный код/quizId, длительность, результаты повторного чтения и проверки дублей. Отдельно — смысловые замечания к вопросам. Для воспроизведения сохраняйте тестовый материал разрешённым способом, без персональных данных и секретов. Не публикуйте JWT, provider key, .env или содержимое конфигурации контейнера.

DoD остаётся открытым до подтверждений: человеческое ревью, зелёный CI проверяемого SHA, повтор по инструкции другим участником и решение замечаний качества. Эта инструкция и локальные тесты не закрывают карточку автоматически.
