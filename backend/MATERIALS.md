# API учебных материалов

Реализованы четыре операции. Префикс `/api` соответствует остальным маршрутам проекта.
Все запросы требуют `Authorization: Bearer <JWT>`; идентификатор владельца берётся
из JWT, а не из тела запроса. Без авторизации возвращается 401. Для чужого и
несуществующего UUID материала возвращается одинаковый 404.

| Метод | URL | Успешный ответ |
| --- | --- | --- |
| POST | `/api/materials` | 201, MaterialDetail, Location на созданный материал |
| GET | `/api/materials/{materialId}` | 200, MaterialDetail |
| PATCH | `/api/materials/{materialId}` | 200, MaterialSummary |
| DELETE | `/api/materials/{materialId}` | 204 без тела |

## Создание

`multipart/form-data` содержит две обязательные части: `file` и `metadata`.
У `metadata` должен быть Content-Type `application/json`.

Пример содержимого `metadata.json` (UTF-8):

```json
{
  "name": "Лекция 1. Основы SQL",
  "subjectName": "Базы данных",
  "description": "Подготовка к экзамену",
  "tagIds": [],
  "newTagNames": ["SQL"]
}
```

Пример в PowerShell, `$token` — JWT из ответа регистрации или входа:

```powershell
curl.exe -i http://localhost:8080/api/materials -H "Authorization: Bearer $token" -F "file=@lecture.pdf" -F "metadata=@metadata.json;type=application/json"
```

`name` обязателен, до 255 символов; `subjectName` обязателен, до 100 символов.
Оба значения обрезаются по краям и не могут состоять из пробелов.
Название материала уникально в пределах пользователя с учётом регистра.
`description` необязателен, до 2000 символов. Суммарно разрешено до 20 переданных
тегов; новые имена — до 50 символов. Предмет и новые теги создаются или
переиспользуются в той же транзакции. `tagIds` должны принадлежать выбранному
предмету пользователя; чужой или отсутствующий тег даёт 404.

Допустимы PDF, DOCX и UTF-8 TXT до 10 MiB; пустые файлы запрещены. MIME клиента
не считается доказательством формата: проверяется сигнатура PDF и маркер EOF,
у DOCX — ZIP-контейнер с непустыми `[Content_Types].xml` и `word/document.xml`,
у TXT — UTF-8, непустой текст и отсутствие бинарных управляющих символов.
Распаковка DOCX ограничена 50 MiB и 2000 ZIP-элементами. Это базовая проверка
формата, а не полноценный разбор документа, проверка на вирусы или извлечение текста.

Новый материал имеет статус `STORED`, progress 0. Анализ, OCR, RAG и LLM в эту
задачу не входят и автоматически не запускаются. `raw_text` остаётся NULL.
POST возвращает 201 вместо прежней заглушки 202. Заголовок `Idempotency-Key`
для этой операции больше не требуется; повтор POST с тем же именем даёт 409.

## Чтение и изменение

```powershell
curl.exe -i "http://localhost:8080/api/materials/$materialId" -H "Authorization: Bearer $token"
```

GET возвращает метаданные, исходное имя файла, теги и состояние обработки.
Публичные URL, ключи S3 и содержимое файла не возвращаются.

PATCH принимает только `name` и `subjectName`. Оба поля обязательны по контракту
проекта; описание, владелец, статус и файл через этот метод не меняются.
Неизвестные JSON-поля отклоняются с 400.

Содержимое `patch.json`:

```json
{"name":"Лекция 1. SQL — обновлено","subjectName":"Базы данных"}
```

```powershell
curl.exe -i -X PATCH "http://localhost:8080/api/materials/$materialId" -H "Authorization: Bearer $token" -H "Content-Type: application/json" --data-binary "@patch.json"
```

При смене предмета прежние теги отсоединяются. Сам прежний предмет и его теги
остаются в справочнике. Параллельные изменения материала защищены блокировкой БД.

## Удаление и обработка сбоев

```powershell
curl.exe -i -X DELETE "http://localhost:8080/api/materials/$materialId" -H "Authorization: Bearer $token"
```

DELETE атомарно удаляет материал и его связи с тегами и записывает задание
очистки файла. После фиксации транзакции выполняется попытка удаления из MinIO.
При ошибке хранилища ответ остаётся 204, материал уже недоступен; сохранённое
задание повторяется в фоне. Повтор DELETE того же материала возвращает 404.
Для будущих активных обработок EXTRACTING/ANALYZING предусмотрен 409.

При создании задание компенсации фиксируется **до** загрузки в S3. Оно блокируется
на время транзакции создания и удаляется вместе с успешной фиксацией материала.
Если загрузка или фиксация не удалась, материал, новый предмет и новые теги
откатываются, а оставшийся объект очищается по сохранённому заданию через 10 минут.
Очередь переживает перезапуск приложения; при недоступности S3 попытки повторяются.
Отдельной распределённой транзакции между PostgreSQL и S3 нет.

Объекты хранятся в приватном bucket под ключом `materials/{userId}/{fileId}`.
Загрузка и удаление используют существующий `service/file/FileStorageService`:
общие методы `uploadFile` и `deleteFile` с областью `FileScope.MATERIALS`.
Обычный файловый API использует ту же реализацию с областью `GENERAL`.
Публичный доступ к bucket включать не нужно. Обычный `/api/files/{id}` использует
другой префикс и не может удалить оригинал материала.

## БД, настройки и запуск

Flyway применяет `V3__Create_Materials.sql`: `materials`, `material_tags` и
`material_file_cleanup`. Приложенная концептуальная схема адаптирована к уже
существующей БД проекта: UUID вместо integer, `subjects` вместо `courses`,
`title` хранит API-поле `name`; вместо публичного `file_url` используется `file_id`.
Добавлены описание, размер файла и исходное имя для существующего API.

Для запуска нужны PostgreSQL и MinIO, а также существующие настройки JWT:

```dotenv
DB_URL=jdbc:postgresql://localhost:5432/study_assistant_db
DB_USERNAME=postgres
DB_PASSWORD=<password>
JWT_SECRET=<existing-secret>
JWT_EXPIRATION=86400000
MINIO_ENDPOINT=http://localhost:9000
MINIO_ACCESS_KEY=<access-key>
MINIO_SECRET_KEY=<secret-key>
MINIO_BUCKET_NAME=materials
MATERIALS_CLEANUP_DELAY_MS=60000
```

Старые имена переменных MinIO поддерживаются как fallback. Bucket создаётся
существующим FileStorageService при запуске. Необходимы права на проверку/создание
bucket и запись/удаление объектов. Схемой управляет Flyway, Hibernate работает
в режиме `validate`. В Compose исправлены имя образа MinIO и сеть сервиса.

Сборка без автотестов с JDK 25:

```powershell
.\gradlew.bat compileJava bootJar -x test
java -jar build/libs/app.jar
```

Основные ошибки: 400 — валидация/некорректный документ; 401 — нет авторизации;
404 — отсутствующий или чужой ресурс; 409 — конфликт имени/связей или активная
обработка; 413 — превышение размера; 415 — неподдерживаемый тип;
503 — сбой загрузки в хранилище. Детали SQL и ключи объектов в ошибки не попадают.

Список материалов, скачивание, массовое удаление и операции анализа остаются
заглушками существующего контракта и не входят в эти четыре операции.
