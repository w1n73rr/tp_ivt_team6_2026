# Backend API MVP

Источник контракта — [backend-api.yaml](backend-api.yaml), OpenAPI 3.0.3.
Все маршруты имеют префикс `/api`. Авторизация — `Authorization: Bearer <JWT>`.
Swagger UI: `/swagger-ui.html`; исходный YAML: `/backend-api.yaml`.

Четыре CRUD-операции материалов реализованы с PostgreSQL и MinIO.
Метаданные, примеры запросов, настройка и семантика очистки файлов описаны в
[MATERIALS.md](MATERIALS.md). POST возвращает 201 и статус STORED без запуска LLM.

## Генерация и реализация

Требуется JDK 25. Gradle Wrapper обновлён до 9.1.0, поддерживающего Java 25.

```powershell
.\gradlew.bat openApiValidate
.\gradlew.bat openApiGenerate
.\gradlew.bat compileJava
```

`compileJava` автоматически проверяет контракт и запускает генерацию. Код появляется
в `build/generated/openapi/src/main/java/tech/genna/TY3/api`: интерфейсы API и пакет
`model` с DTO. Генерируемые файлы не коммитятся и не редактируются вручную.
После изменения YAML достаточно пересобрать проект или выполнить `openApiGenerate`.

Контроллеры реализуют эти интерфейсы. Уже работающие регистрация, вход, создание и
чтение предметов/тегов и четыре CRUD-операции материалов используют сгенерированные DTO. Остальные методы доступны как
заготовки `501 Not Implemented` без тела. Для реализации переопределите соответствующий
метод интерфейса в контроллере; `MvpController` можно постепенно разделять по областям.
Наличие метода в Swagger не означает, что его бизнес-логика реализована.

Проверки контракта и сервисов без БД:

```powershell
.\gradlew.bat test --tests "tech.genna.TY3.controller.GeneratedApiContractTest" --tests "tech.genna.TY3.service.*" bootJar
```

HTTP-проверки сверяют регистрацию всех сгенерированных операций, `items`, ошибки,
валидацию, существующий запрос регистрации и ответ `501` заготовок. Старые тесты
с `@SpringBootTest` требуют отдельной настроенной PostgreSQL и переменных окружения.

MinIO используется для файлов и материалов. Вызовы LLM, анализ, генерация
и отправка почты остаются вне реализованной части API.

## Формат списков и ошибок

Согласно подробной спецификации аналитиков списки материалов, предметов и тегов
обёрнуты в `items`. Это изменение относительно прежних ответов предметов/тегов
в виде голого массива; frontend должен читать `response.items`.

```json
{"items":[{"id":"d290f1ee-6c54-4b01-90e6-d701748f0851","name":"Математика"}]}
```

Пустой справочник — `200` с `{"items":[]}`. Ошибка никогда не заменяется пустым списком.
История попыток дополнительно содержит `page`, `size`, `totalElements`.

```json
{"code":"MATERIAL_NAME_ALREADY_EXISTS","message":"Материал с таким названием уже существует."}
```

Все штатные ошибки API имеют `code` и `message`; ошибки полей могут содержать
`fieldErrors: [{"field":"name","message":"..."}]`. `401` означает необходимость входа,
`403` — запрет операции, `404` — отсутствие ресурса или доступа к чужой записи,
`409` — конфликт состояния/уникальности, `413` — большой файл, `415` — неверный формат,
`429` — лимит с `Retry-After`, `502/504` — неуспешный ответ/таймаут LLM.
`501` — временный ответ сгенерированной заготовки; тела у него нет.

## Файлы, MinIO и внешняя нейросеть

Загрузка: `POST /api/materials`, multipart-части `file` и `metadata`.
`metadata` имеет Content-Type `application/json`, поля `name`, `subjectName`,
необязательные `description`, `tagIds`, `newTagNames`. В Docker MinIO будет отдельным
S3-совместимым сервисом. В БД сохраняются метаданные и приватный object key, а не байты.
Браузер получает оригинал через авторизованный backend; постоянных публичных S3 URL
и учётных данных хранилища в API нет. DOCX доступен для скачивания, но не inline-просмотра.

Отправка файла и сохранение метаданных требуют компенсации при сбое между S3 и БД.
Одиночное и массовое удаление не должны каскадно уничтожать результаты тестов.
История сохраняет снимки названий, вопросов и ответов. Массовое удаление — «всё или
ничего» для пользователя; физическое удаление объектов требует собственного
согласованного механизма, поскольку транзакция БД не охватывает MinIO.

Анализ материала и генерация тестов асинхронны: `202` → polling каждые 2 секунды.
Ошибки фоновой задачи содержат `code`, `message`, `retryable`; успешное получение
состояния не становится HTTP 5xx из-за статуса `FAILED`.
Для защищённых от дублирования POST требуется UUID `Idempotency-Key`.

LLM-провайдер, URL, ключ и модель задаются серверной конфигурацией. Клиент оперирует
учебными настройками, а не провайдерами. В дальнейшем внешний API можно заменить
адаптером собственной модели. Ответ LLM проверяется сервером до сохранения теста;
оценивание в MVP не требует вызова LLM. Правильные варианты и объяснения не выдаются
до завершения попытки; подсказки также не должны раскрывать ключ ответа.

## Источники и принятые решения

Прочитаны все пять документов из локальной `local-docs`:

| Документ | Использованные требования |
| --- | --- |
| Видение проекта | Цель MVP, три типа вопросов, материалы около 5–10 страниц |
| Пользовательские роли и сценарии | Студент как владелец материалов и результатов; команда/тестировщик не отдельные продуктовые роли |
| Базовая структура приложения | Все 18 экранов: авторизация, материалы, тестирование, аналитика, профиль, настройки |
| Загрузка материала | PDF/DOCX/TXT, название, предмет, описание, теги, создание предмета и тегов |
| Мои материалы | Точные поля списка, items, frontend-поиск/фильтры, просмотр/скачивание, PATCH, уникальность, bulk-delete и личные каталоги |

При расхождениях подробная спецификация материалов имеет приоритет над общим макетом:
один материал на тест, только PDF/DOCX/TXT, редактируются только название и предмет.
Открытые вопросы и PPTX из общего макета отложены: их нет в согласованном перечне MVP.
Google-вход, восстановление пароля и аватар присутствуют в общем макете и включены
как отдельные заготовки; они требуют последующего подключения Google, почты и S3.
Отдельные сомнительные экраны обработки не обязательны для frontend, но состояния
и темы доступны через API для генерации и polling.

Точные лимиты, не определённые аналитиками, зафиксированы как проектные решения
контракта и могут быть изменены до реализации: документ 10 MiB, PDF до 10 страниц,
не более 30000 Unicode code points извлечённого текста для любого формата,
аватар 5 MiB, до 20 тегов, до 100 ID при bulk-delete,
Idempotency-Key хранится 24 часа, reset-токен действует 15 минут, слабая тема имеет
точность ниже 70%. Для нового пользователя рекомендуемые настройки — 10 вопросов,
MEDIUM, ru, подсказки включены, объяснение SHORT/SIMPLE.

Клиентское подтверждение пароля проверяется на frontend: API принимает один пароль.
Уникальность имени материала чувствительна к регистру, сравнение выполняется после
trim. При переносе между предметами теги прежнего предмета отсоединяются атомарно;
новые теги не создаются автоматически при PATCH.
