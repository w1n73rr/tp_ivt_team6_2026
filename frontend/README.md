# Frontend — запуск и передача работы

Обновлено 18.11.2026. Принятая база: `dev`, `7c19309`.
Angular 22, TypeScript 6, Angular Material/CDK, SCSS, RxJS; Node.js 24 и npm.
Эта инструкция позволяет продолжить работу без доступа к переписке автора.

## Что работает и что предстоит

В принятом `dev` подключены реальные регистрация/вход, материалы (загрузка,
просмотр, скачивание, переименование и удаление), поиск/фильтры материалов,
настройки генерации, запуск и опрос статуса, состояния успеха/ошибки,
список собственных тестов, переименование/удаление, поиск и сортировка
по названию, материалу и дате. ID скрыт и не сортируется.
Тест готов только после чтения сохранённого результата; неполный результат — ошибка.

В `dev` ещё нет frontend прохождения и результата: «Пройти тест» показывает
сообщение-заглушку, «Перейти к тесту» на готовности отключено. Backend попыток
уже содержит запуск/продолжение, запись ответа, завершение и `/result`.
История и профиль запланированы отдельно. Тренировка, прогресс и настройки отложены.

Задача №119 подготовлена в `feature/tpivt6_26-119-session-protection`:
защита всех личных маршрутов, очистка при выходе/смене сессии, отмена старых
запросов, обработка 401 и истечения JWT. До слияния эти изменения доступны
только в этой ветке. Для остальных задач нужны отдельные PR.

## Запуск всего приложения из чистой копии

Нужны Git, Docker Desktop с Linux-контейнерами, Compose >= 2.24.4.
Для полного Docker-запуска локальные Node.js и JDK не нужны.
Команды PowerShell выполняются из корня репозитория:

```powershell
git clone https://ssau.saas.sferaplatform.ru/app/sourcecode/api/tp_ivt_team6_2026/tp_ivt_team6_2026.git
cd tp_ivt_team6_2026
git switch dev
git pull --ff-only origin dev
if (!(Test-Path .env)) { Copy-Item .env.example .env }
```

В `.env` задайте четыре независимых случайных значения для `POSTGRES_PASSWORD`,
`JWT_SECRET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`. Для каждого можно выполнить в PowerShell:
`[Convert]::ToHexString([Security.Cryptography.RandomNumberGenerator]::GetBytes(32))`.
Не заменяйте значения существующей базы и не копируйте секреты в Git или отчёты.
Шаблон `.env.example` содержит остальные настройки; изменять frontend для ключа ML не нужно.

Для настоящей генерации выберите один вариант:

- `ML_PROVIDER=openrouter`, `OPENROUTER_API_KEY`, `OPENROUTER_MODEL`;
- `ML_PROVIDER=cloudru`, `CLOUDRU_API_KEY`, `CLOUDRU_MODEL`.

Ключ остаётся только на backend. Без ключа выбранного провайдера вход и CRUD
доступны, но генерация завершится `NOT_CONFIGURED`. Реальные запросы модели
могут расходовать квоту/средства; обычные unit/CI-проверки их не выполняют.

```powershell
docker compose config --quiet
docker compose up -d --build --wait
docker compose ps
```

Откройте http://localhost:3000, зарегистрируйте собственную тестовую учётную запись.
Backend по умолчанию http://localhost:8080. Порты задаются в `.env`.
Nginx внутри frontend направляет `/api/` в backend; не запускайте этот образ
одиночным `docker run` без сети и имени `exam-ai-backend`.

`docker compose down` останавливает приложение с сохранением volumes.
Не используйте `down -v` для обычной остановки. Перед обновлением существующей БД
сделайте резервную копию и сверьте миграции: Flyway запускает их вместе с backend.
Переключение ветки не обновляет контейнер: после смены исходников нужна сборка.

Для проверки этой задачи вместо `dev` выберите опубликованную ветку №119 и
повторите сборку. На рабочем стенде обновляйте только согласованную версию;
не запускайте тесты и миграции на чужой существующей БД.

## Работа над интерфейсом без сборки Docker

Нужны Node.js 24 и npm. Backend должен уже работать. Для соединения с API
Angular-серверу нужен proxy: пример `frontend/proxy.conf.json` направляет
`/api` на `http://localhost:8080`. При другом порте измените локальную копию.
Добавьте `http://localhost:4200` в `APP_CORS_ALLOWED_ORIGINS` backend вместе
с адресом Docker-интерфейса, затем пересоздайте backend с этой настройкой.

```powershell
npm --prefix frontend ci
npm --prefix frontend start -- --proxy-config proxy.conf.json
```

Интерфейс: http://localhost:4200. Без proxy сам интерфейс откроется,
но запросы `/api` не попадут на backend. Основной воспроизводимый путь — Compose выше.

## Сессия и безопасность (№119)

JWT и ник хранятся в `sessionStorage` текущей вкладки и восстанавливаются при F5.
При запрете хранилища сессия живёт только в памяти. Изменение хранилища не даёт
прав на backend. Клиент читает `exp` только для очистки интерфейса;
подпись, срок и владельца проверяет сервер.

Запросы `/api/` относятся к конкретной ревизии сессии. При выходе или замене
учётной записи они отменяются, личный экран скрывается, диалоги закрываются,
черновики/отложенный файл очищаются, открытые приложением предпросмотры закрываются,
объектные URL отзываются. Поздний ответ прежней сессии не обновляет новую.
401 закрывает сессию; 403/404 не объявляются истечением токена и не раскрывают
внутренний текст backend. Для внешнего URL перехватчик не добавляет JWT.
Возврат после входа разрешён только на явно поддержанные локальные маршруты.

Названия и текст выводятся через Angular-интерполяцию. Не используйте
`innerHTML`/обход санитайзера для пользовательского или ML-текста.
Уже скачанный файл не удаляется с компьютера при выходе. Logout очищает
клиентскую вкладку; отзыв токена на сервере и синхронизация независимых вкладок
не добавлялись этой задачей.

## Проверки и ручная приёмка

Из корня:

```powershell
npm --prefix frontend test -- --watch=false
npm --prefix frontend run build
```

Тесты сессии: `src/app/core/auth/session-protection.spec.ts`; файлы и предпросмотр:
`src/app/features/materials/material-files.spec.ts`. Проверки не используют реальный ML.
Предупреждения сборки о текущем размере bundle, SCSS и CommonJS JSZip
сохраняются; это предупреждения, не успешная проверка без замечаний.

Проверка в Compose для №119:

1. В новой/приватной вкладке открыть напрямую `/tests`, `/materials`,
   `/materials/upload`, `/dashboard` и ссылку настройки генерации. Ожидается вход;
   список и название материала до входа не показаны.
2. Войти как A, загрузить TXT/PDF/DOCX, проверить материалы и собственные тесты.
   Название с `<img ...>` отображается текстом, HTML не исполняется.
3. Выйти с открытым личным экраном/диалогом; проверить очистку интерфейса,
   возврат назад и F5. Закрытый предпросмотр не должен вновь открыться от старого ответа.
4. Войти как B. Записи, черновики и файл A не должны появиться. Чужой ID
   должен дать безопасный отказ backend; не вставляйте JWT в адресную строку.
5. Автотесты дополнительно проверяют поздний HTTP-ответ, 401, истечение `exp`,
   смену аккаунта без промежуточного logout, очистку памяти/хранилища и внешний URL.

Для основного пути генерации: материал → «Создать тест» → название/параметры →
запуск → реальные три этапа → сохранённый тест → «Все тесты» → F5 →
переименование/удаление. При `QUALITY_REJECTED`, `INVALID_MODEL_OUTPUT`,
`MODEL_OUTPUT_LIMIT` сервер отклонил результат модели: это не отсутствие
авторизации. При ошибке сохраняются настройки текущего входа;
процент ожидания не выдумывается.

## Как продолжить задачу и передать её участнику

Сначала получите свежий `dev` в чистой рабочей папке (`git status`), затем:

```powershell
git fetch origin
git switch dev
git pull --ff-only origin dev
git switch -c feature/tpivt6_26-<номер>-<краткое-имя>
```

Коммиты: `feat: ...`, `fix: ...`, `test: ...`, `docs: ...` с русским описанием.
Одна задача — одна ветка. После тестов отправьте её в Сферу и существующее
зеркало GitHub (`git push -u origin HEAD`, `git push github HEAD`). Дождитесь
зелёного CI именно этого SHA. Для полной проверки в Actions «Проверка проекта»
выберите эту ветку, `full=true`, `negative_smoke=false`.

PR создаётся в Сфере в `dev`. В описание и связанные артефакты задачи добавьте:
изменение/границы, SHA, CI-ссылку, проверки, инструкцию Compose и ограничения.
Ревью другого участника, его аппрув и повторение README не заменяются ИИ.
После слияния снова fetch, проверьте принятый `origin/dev` и передайте именно его SHA
в GitHub (`git push github origin/dev:refs/heads/dev`, без force).
Следующую задачу начинайте от принятого `dev`. Удаляйте завершённую ветку
только после сверки слияния и отсутствия незавершённой работы.

Релиз в `master` — отдельный PR из согласованного `dev` после проверок;
не направляйте feature-PR сразу в `master`. Сервер и публикация образов — отдельный этап.

Порядок текущих задач: №119 → №102 → №101 → №103 → №104 → №111 → №105 → №112 → №113.
Экран №102 нужен переходу №101, а базовый результат №111 — переходу завершения №105.
Прежде чем закрыть задачу, сверяйте живые AC/DoD и подтверждения в её карточке.
